# llm-code-slicer — AI には関係するコードだけを渡す

[English](README.md)

AI に変更の確認や修正を頼むとき、ふつうはファイルを丸ごと貼ります。5,000 行のファイルなら1回で約10万トークン、しかも大半は変更と関係のない所です。`slice_funcs.py` は Python のファイルを読んで関数どうしのつながりの地図を作り、変えた行から出発して、つながる所だけを行番号つきで切り出します。そのまま AI に貼れます。

- Python 3.9 以上、標準ライブラリ（`ast`）だけ。インストール不要、通信なし。
- 1つのファイルが単位。出力は `パス:開始-終了` の範囲、目次、線の一覧。
- 部品式: つながりの種類ごとに小さな部品。部品を1つ足せば新しい書き方に対応できる。

## 関連の強さで選ぶ

`--select relevance` を付けると、つながる関数ごとに部品式の物差しで点数を付け、点数の高い順に予算まで足します。変わった関数は必ず入ります。大きな関数は、変更につながる行（と `def`・docstring）だけに切り詰めます。

| 物差し | 点数が高くなるとき |
|---|---|
| `distance` | 変わった関数に近い（呼び元と呼び先は別々に数える） |
| `edge_kind` | 名前が出てくるだけでなく、直接呼んでいる |
| `shared_state` | 同じ `self.x`・モジュールの変数・定数を読み書きしている |
| `diff_terms` | 変えた行に出てくる名前や文字列が出てくる |
| `cochange` | git の履歴で、同じコミットで一緒に変わっている（`--git-root`） |

重みは `--weights 名前=値,...` で変えられ、新しい物差しは小さな部品を1つ足すだけで増やせます。

## たどるつながり

| 種類 | 例 |
|---|---|
| `call` | `f()`、`self.f()`、`cls.f()`、`Class.f()` |
| `ctor` | `Class(...)` → `Class.__init__` |
| `typed_attr` | `x = Runner(); x.run()`（型が分かるときだけ） |
| `ref` | 値として渡す関数（コールバック、`{"名前": 関数}`） |
| `alias` | `cmd_sol = cmd_sol_r3`（最後に代入された実体へ） |
| `dispatch` | argparse の `set_defaults(func=cmd_x)` → `args.func(args)` |
| `nested` | 関数の中で定義した関数 |
| `decorator` | デコレータ → 飾られた関数 |

import したモジュールの呼び出し（`subprocess.run`、`os.path…`）や型の分からない受け手はわざとたどりません。`obj.run()` が自分の `run` メソッドに誤ってつながらないようにするためです。

## 使い方

```sh
# 差分につながる範囲（上りと下りを別々にたどる）
python3 slice_funcs.py --file app.py --diff change.diff

# main から下りだけで、層ごとにどこまで届くか
python3 slice_funcs.py --file app.py --names main --direction down --layers --metric code

# 切り出しをファイルの1割に抑える
python3 slice_funcs.py --file app.py --diff change.diff --max-lines 600

# 関連の強い順に1割の予算まで選び、点数の内訳を表示する
python3 slice_funcs.py --file app.py --diff change.diff --select relevance --budget 10% --git-root . --explain

# 自己検査を実際に動かして記録した本物の呼び出しと、静的な地図を照らし合わせる
python3 trace_calls.py --file app.py -- --self-test > real.tsv
python3 slice_funcs.py --file app.py --compare-trace real.tsv
```

## 実測（どれも1回ずつ・1つのリポジトリでの結果。目安として。全ての表は [BENCHMARKS.ja.md](BENCHMARKS.ja.md)）

**地図は本物と合っているか**（各ファイルの自己検査を `sys.settrace` の下で動かして本物の呼び出しを記録）

| ファイル | 行数 | 本物の呼び出しとの一致 |
|---|---|---|
| argparse で振り分ける CLI | 5,811 | 99%（183組中182） |
| 反映スクリプト | 3,351 | 93%（76組中71） |

**プログラムはピラミッドか**（`main` から下りだけ。数層で大半に届き、真ん中の層がいちばん厚い）

| ファイル | 行数 | `main` から届く範囲 | 頭打ちの層 |
|---|---|---|---|
| ジョブの本体 | 10,226 | 90% | 6 |
| CLI | 5,811 | 95% | 5 |
| 反映スクリプト | 3,351 | 95% | 4 |

**確認する側はどれだけのコードが要るか**（同じ36行の変更・同じ依頼文を、中くらいのモデル（medium）に、渡す量だけ変えて確認させた）

| 渡した量 | 行数 | 入力 | 判定 | 主な指摘 |
|---|---|---|---|---|
| 関連の強さで選択 | 418（7%） | 約2.5万 | PASS | 同じ要点＋全文で出なかった指摘1つ |
| 1割の切り出し（行数の上限） | 606 | 約2.7万 | PASS | 同じ要点 |
| 2割の切り出し（行数の上限） | 1,194 | 約3.7万 | PASS | 同じ要点 |
| 全文 | 5,811 | 約10.5万 | PASS | 同じ要点 |

関連の強さで選ぶと、全文の約4分の1の入力で要点を拾い、渡していない所は推測せず「見えない」と書いた。回ごとの重さの付け方の違いはモデル側のぶれで、渡した量とは関係が見えなかった。

## 限界

- 変数に入れた関数を後で呼ぶ、`getattr` などの動的な呼び出しは一部しか見えない。
- 変更が1,000行を超える巨大な関数に入ると、それだけで量が増える。
- 1ファイルずつ。
